# HeatIQ Backend

**SIH26083 · Localized Human Thermal Stress & Health Risk Early Warning Platform**

HeatIQ is a backend pipeline that turns weather and contextual data into **ward-level human heat-risk intelligence** and then converts a selected ward's calculated state into an operational recommendation.

The backend is organized around two separate runtime flows:

```text
PLACE NAME
    ↓
 Main Gate
    ↓
  Wire 1
    ↓
Thermal + Prediction + Mortality
+ Info Pool + Resource Pool
    ↓
  Ward Filter
    ↓
Ward-level intelligence
    ↓
 Wire 1 Store
    ↓
CLI / Dashboard
    │
    │ select area_id
    ▼
  Wire 2
    ↓
Recommendation Engine
    ↓
 Gemini
    ↓
RecommendationOutput
    ↓
Main Gate
    ↓
CLI / Dashboard
```

---

## What the Backend Does

### 1. Accepts a location

A place name such as:

```text
Bhubaneswar
```

is sent to the **Main Gate**, which routes it into **Wire 1**.

### 2. Builds the environmental state

The data foundation supplies the weather/history information required by the analytical pipeline.

The prototype uses multi-day hourly data for the prediction workflow.

### 3. Calculates thermal stress

The **Thermal Engine** works with environmental inputs and produces thermal metrics including:

- WBGT
- UTCI
- Heat Index
- HTSI

HTSI represents the project's Human Thermal Stress state.

### 4. Produces health-risk information

The **Mortality / Health Risk** layer provides population/area-level mortality-risk information.

It is not an individual probability of death.

### 5. Produces future-risk information

The **Prediction / ML Engine** uses the configured historical/current feature window to produce forward-looking heat-risk information, including:

- probable future heat risk
- heat-risk window / duration

### 6. Adds population information

The **Info Pool** provides ward-level population, vulnerability, occupation, demographic, and other available contextual information.

### 7. Adds response resources

The **Resource Pool** provides ward-level response-capacity information.

The current Bhubaneswar prototype contains records for:

```text
WARD_001 → WARD_060
```

The current Resource Pool prototype uses fields such as:

```text
hospital_count
hospital_capacity
cooling_centre_count
distance_to_healthcare_km
resource_capacity_score
```

These are prototype/mock values, not authoritative government data.

### 8. Builds a WardContext

**InfoSmasher** combines the structured outputs belonging to one ward:

```text
ThermalOutput
PredictionOutput
MortalityOutput
InfoPoolRecord
ResourcePoolRecord
        ↓
    WardContext
```

It validates that all records belong to the same `area_id`.

InfoSmasher assembles and validates data. It does **not** decide severity.

### 9. Classifies the ward

The **Ward Filter** applies deterministic rules to the WardContext.

It considers signals such as:

- HTSI
- mortality risk
- vulnerability information where available
- resource capacity
- prediction hazard score

It produces structured ward intelligence including things such as:

- severity
- condition message
- triggered conditions
- recommended actions
- calculation status
- method version

Missing data is handled at the rule level. A rule requiring a missing field can be skipped without disabling unrelated rules.

### 10. Stores Wire 1 results

Wire 1 stores the generated ward context/results so they can be inspected and subsequently consumed by Wire 2.

---

# Wire 1

Wire 1 is the **location → ward intelligence** pipeline.

Its job is to process an entire requested location and generate the ward-level state.

Conceptually:

```text
Bhubaneswar
    ↓
Wire 1
    ↓
60 wards
    ↓
60 WardContexts / WardFilterResults
```

Once Wire 1 has run, you can inspect the raw ward-level output.

### Important

**Wire 2 depends on Wire 1.**

You cannot request a recommendation for a ward whose WardContext has not been generated.

---

# Wire 2

Wire 2 is the **ward → recommendation** pipeline.

When you enter an `area_id`, for example:

```text
WARD_059
```

Wire 2:

1. retrieves the existing `WARD_059` context generated by Wire 1
2. does **not** rerun Wire 1
3. sends the selected ward's structured information to the Recommendation Engine
4. the Recommendation Engine sends the ward information to Gemini
5. Gemini generates an operational recommendation
6. the result becomes a `RecommendationOutput`
7. Wire 2 keeps the recommendation in runtime state
8. Main Gate returns it to the client

A recommendation for one ward must never be returned for another ward.

---

# Recommendation Engine

The Recommendation Engine is **not** the deterministic risk calculator.

The Ward Filter has already determined the ward's condition.

The Recommendation Engine answers:

> Given this ward's calculated thermal state, health risk, population context, prediction, and available resources, what should authorities do?

Gemini can produce recommendations covering:

- immediate actions
- vulnerable population priorities
- cooling-centre use
- healthcare preparation
- hydration/water support
- outdoor-worker protection
- resource positioning
- outreach
- monitoring
- escalation

The recommendation is expected to explain:

```text
WHAT to do
WHY to do it
HOW to do it
WHAT to prioritize
WHAT resources to allocate
WHERE to allocate them
WHAT to monitor
WHEN to escalate
```

Gemini must work from the supplied ward information and should not invent facilities, capacities, population numbers, or resources that were not provided.

# Main Gate

The Main Gate is the backend's entry point and routing boundary.

It handles:

- API-key creation
- API-key storage
- API-key revocation
- request authentication
- input routing
- backend server startup
- forwarding place names to Wire 1
- forwarding area IDs to Wire 2
- returning the appropriate result

The routing logic is:

```text
place name
    ↓
 Wire 1

area_id
    ↓
 Wire 2
```

From the project root:

```bash
python -m backend.maingate.run
```

Keep this terminal running.

You should be able to see backend activity in the terminal while requests are being processed.

# Using the CLI

Open a **second terminal** in the project root.

Start the CLI:

```bash
python -m cli.main
```

The CLI connects to the local backend through the Main Gate API.

It does not bypass the backend and directly import the internal pipeline for normal requests.

---

## CLI Authentication

When prompted, enter an API key issued by the Main Gate.

The CLI uses secure input for the key.

---

## Run Wire 1

Type:

```text
input Bhubaneswar
```

The CLI sends the place name to the backend.

The backend runs Wire 1 and generates the ward-level results.

The CLI then displays the raw ward-level Ward Filter output.

You should see the actual calculated information rather than only a list of ward numbers.

---

## Request a Recommendation

After Wire 1 has completed, enter a ward ID:

```text
WARD_059
```

This invokes Wire 2.

The backend retrieves the existing `WARD_059` context and sends that ward's information through the Recommendation Engine.

The resulting Gemini recommendation is returned to the CLI.

The CLI renders the recommendation as Markdown.

For example:

```text
WARD_059

Situation
---------

...

Immediate Actions
-----------------

1. **Action**
   - Why
   - How

2. **Action**
   - Why
   - How

Resource Allocation
-------------------

- ...
- ...
```

The exact content depends on the ward data and Gemini response.

---

## Request Another Ward

You can immediately enter another area ID:

```text
WARD_060
```

Then:

```text
WARD_012
```

Then:

```text
WARD_030
```

Wire 1 does **not** need to run again.

Each request retrieves the corresponding ward's stored context and generates a recommendation specifically for that ward.

# Dashboard / Frontend

The frontend communicates with the backend through the **Main Gate API**.

It should not directly import backend modules such as:

```text
Thermal Engine
Ward Filter
Wire 1
Wire 2
Recommendation Engine
```

The frontend is a client of the backend.

The current dashboard concept is intentionally minimal.

It provides:

- HeatIQ branding
- a central search/input control
- API-key creation
- API-key revocation
- result/recommendation display

The API-key interface is designed around two simple actions:

### Create a key

Press the `+` button.

A popup displays the newly generated API key and provides a copy-to-clipboard action.

### Revoke a key

Enter the issued key in the key/revocation input and use the revoke action.

A confirmation popup asks whether the key should be revoked.

The backend remains responsible for actually validating and revoking the key.

# API Keys

The Main Gate maintains issued API keys.

The lifecycle is:

```text
Create
  ↓
Issue unique key
  ↓
Store key
  ↓
Use key for requests
  ↓
Revoke when required
```

Keys are authentication credentials.

Do not place API keys inside:

- WardContext
- Gemini prompts
- Resource Pool data
- Info Pool data
- frontend source code
- public repositories

# Backend Storage Model

There are two important runtime boundaries.

## Wire 1

Wire 1 stores the generated ward contexts/results so that they can be consumed after location processing.

```text
Wire 1
  ↓
WardContext / WardFilterResult
  ↓
Wire 1 store
```

## Wire 2

Wire 2 keeps recommendation state at runtime.

```text
WardContext
  ↓
Gemini recommendation
  ↓
RecommendationOutput
  ↓
Wire 2 runtime state
```

Wire 2 recommendations are not intended to become a permanent replacement for the canonical WardContext.

---

# Architecture Boundaries

These responsibilities should remain separate.

| Component | Responsibility |
|---|---|
| Main Gate | Authentication, API access, routing |
| Wire 1 | Location → ward intelligence |
| Thermal Engine | Thermal calculations |
| HTSI | Human thermal stress representation |
| Mortality | Population-level health risk |
| Prediction Engine | Future heat-risk prediction and window |
| Info Pool | Population/vulnerability/exposure context |
| Resource Pool | Response-resource context |
| InfoSmasher | Assemble + validate WardContext |
| Ward Filter | Deterministic ward classification |
| Wire 1 Store | Store generated ward intelligence |
| Wire 2 | Ward → recommendation |
| Recommendation Engine | Turn ward intelligence into operational action |
| Gemini | Generate detailed natural-language recommendation |
| RecommendationOutput | Structured recommendation result |
| Wire 2 Runtime | Temporary recommendation state |
| CLI | Backend testing/demo client |
| Dashboard | Frontend presentation/client |

# Important Design Rules

### Wire 2 must not rerun Wire 1

If `WARD_059` already exists in Wire 1 storage, Wire 2 should retrieve it.

### Gemini must not replace the Ward Filter

The Ward Filter determines the deterministic severity.

Gemini provides operational decision support.

### Gemini must receive the selected ward

If the user enters:

```text
WARD_059
```

Gemini must receive `WARD_059`'s context, not all 60 wards and not a generic Bhubaneswar payload.

### Ward contexts must remain isolated

`WARD_059` data must never leak into the recommendation for `WARD_060`.

### Missing data should not collapse unrelated rules

If a particular field is unavailable, only rules requiring that field should be skipped.

### Prototype data is not authoritative

Mock Info Pool / Resource Pool values are for demonstration and testing unless explicitly replaced by authoritative sources.

# Troubleshooting

## `ward_context_not_available`

Wire 2 was requested before Wire 1 generated the requested ward.

Run:

```text
input Bhubaneswar
```

first.

Then enter the ward ID.

---

## Resource Pool missing

Check that the prototype resource dataset exists and contains:

```text
WARD_001
...
WARD_060
```

The current expected source is:

```text
datalake/data/bhubaneswar_mock_resources.csv
```

The generated cache should not be treated as the primary source of truth.

---

## Recommendation unavailable

Check the backend terminal first.

The useful debugging path is:

```text
CLI
 ↓
Main Gate
 ↓
Wire 2
 ↓
WardContext retrieval
 ↓
Recommendation Engine
 ↓
Gemini provider
 ↓
RecommendationOutput
```

Do not immediately modify Wire 1 or Ward Filter if Wire 2 is failing.
