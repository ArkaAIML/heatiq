# HeatIQ Backend Bug Testing & Audit Report

## Status
**Checkpoint after Phase 9, before Main Gate implementation**

This report records the architecture validation, integration testing, known findings, and remaining work completed so far.

## 1. Executive verdict

The HeatIQ backend orchestration is now substantially integrated and has passed multiple layers of audit and testing:

- Wiring architecture
- Data-contract tracing
- Wire 1 execution flow
- Wire 2 execution flow
- Prediction integration boundary
- Ward Context Store
- Cross-ward isolation
- Failure/partial-failure behavior
- Real atmospheric acquisition
- Parser hardening
- End-to-end integration

The backend is **not yet final**. The remaining work is concentrated around real data, the external Recommendation ML contract, freshness semantics, and the Main Gate.

## 2. Current architecture

    ↓
ThermalOutput
    ↓

### Wire 2

```text
area_id
    ↓

    ↓

    ↓

    ↓

    ↓
Recommendation ML / dummy boundary
    ↓

```

Wire 2 intentionally does **not** rerun Thermal, Prediction, Mortality, or Ward Filter.

## 3. Important architectural clarification

The Thermal Engine intentionally works from a location/city-level atmospheric condition.

Therefore:

```text
Bhubaneswar atmospheric condition
        ↓
Thermal hazard
        ↓
ward-specific demographic/resource context
        ↓
Mortality + Prediction + Ward Filter
        ↓
ward-specific risk
```

A single legitimate Bhubaneswar atmospheric observation being applied across wards is therefore **intentional**, not a defect.

F-021 has been reclassified as an accepted architectural decision.

### Phase 9 integration

The complete pipeline was tested as:

```text
Bhubaneswar
 → Wire 1
 → atmospheric acquisition
 → Thermal
 → Prediction
 → Mortality
 → Ward Filter
 → Ward Context Store
```

Then:

```text
WARD_001
 → Wire 2
 → Ward Context Store
 → Recommendation boundary
 → RecommendationOutput
```

### Cross-ward isolation

Distinct ward contexts were used, including:

```text
WARD_001
    population = 50,000
    hospitals  = 2

WARD_002
    population = 30,000
    hospitals  = 0
```

Tests verified that ward-specific data remains associated with the correct `area_id`.

### Failure testing

Tested scenarios include atmospheric failure, malformed data, missing thermal information, Info Pool failure, missing ward context, and recommendation failure.

Partial failure was also tested so one bad ward does not destroy valid sibling wards.

Example:

```text
WARD_001 → valid
WARD_002 → insufficient data
WARD_003 → valid
```

### No-recomputation test

Wire 2 was verified not to invoke the full pipeline again.

This prevents the architecture from becoming:

```text
Wire 2
 → Thermal
 → Prediction
 → Mortality
 → Ward Filter
 → Recommendation
```

Instead it remains:

```text
Wire 2
 → stored WardContext
 → Recommendation
```

## 5. Real atmospheric acquisition

Phase 6 replaced the mock atmospheric path with a real provider boundary.

Current architecture:

```text
Bhubaneswar
    ↓
Data Acquisition
    ↓
Open-Meteo
    ↓
provider response
    ↓
canonical ThermalInput
    ↓
Thermal Engine
```

The provider-specific logic is isolated from Thermal mathematics.

The mock provider remains available for deterministic tests.

No API credentials are hardcoded.

## 6. Parser/Data Lake hardening

Phase 8 hardened structured-data ingestion.

Implemented/tested formats include:

- CSV
- TSV
- JSON
- NDJSON
- XLSX
- Parquet
- ZIP-wrapped supported structured files

The parser also handles header normalization, nulls, nullable integer preservation, timestamps, numeric normalization, area_id validation, geographic scope, schema validation, partial failures, and source-specific mappings.

It intentionally does **not** claim to parse arbitrary PDFs, scans, images, or arbitrary web pages.

## 7. Current terminal output

The current live command successfully reaches Wire 2, but the printed Recommendation result is intentionally dummy:

```json
{
  "area_id": "WARD_001",
  "priority": "UNKNOWN",
  "actions": [],
  "reason_codes": [],
  "status": "DUMMY",
  "message": "Recommendation engine unavailable..."

```

This does **not** mean the Thermal Engine is dummy.

The Thermal calculation happens earlier in Wire 1.

The current runner simply does not print the complete ThermalOutput/WardContext.

## 8. How to see actual heat-index values

The correct solution is to expose the already-computed canonical data through the diagnostic runner:

```text
actual ThermalOutput
       ↓
diagnostic serialization
       ↓
terminal
```

Do **not** manually paste heat-index values into the output.

The eventual diagnostic output should expose actual fields from the existing canonical schemas, such as the available thermal indices, atmospheric inputs, prediction status, mortality result, Ward Filter result, timestamps, and area_id.

Exact field names must come from the repository's schemas.

## 9. Remaining findings

### F-010 — Recommendation ML contract
**OPEN / PENDING EXTERNAL MODEL CONTRACT**

The HeatIQ-side Recommendation boundary receives WardContext, but the real Recommendation model contract is not yet available.

Do not invent its input/output schema.

The current dummy compatibility path may reduce the context to what dummyML accepts. This is expected to remain temporary.

### F-011 — Freshness semantics
**PARTIALLY RESOLVED**

Freshness metadata exists, but the final policy has not been finalized.

Do not invent an arbitrary TTL merely to close this finding.

### F-012 — dummyML schema limitation
**PARTIALLY RESOLVED**

dummyML remains intentionally prototype-oriented. Adapters isolate it from the rest of the system.

### F-020 — Real Bhubaneswar demographic data
**OPEN / BLOCKED / DEFERRED**

The current demographic data is controlled prototype data, not the final real Bhubaneswar Census dataset.

The real source still needs to be acquired, mapped to canonical `area_id`, validated, and integrated.

### F-022 — Prediction failure representation
**INFORMATIONAL**

Prediction and Recommendation currently represent failures differently. Revisit this when final ML contracts are integrated.

### F-021
**ACCEPTED ARCHITECTURAL DECISION**

City-level atmospheric acquisition is intentional.

### F-014
**RESOLVED**

Nullable demographic integer handling has regression coverage and avoids unintended float conversion caused solely by missing values.

## 10. What is intentionally NOT final

## 13. Final engineering assessment

The system has progressed from isolated module scaffolding to a tested, integrated orchestration pipeline.

The strongest evidence is not merely that unit tests pass. The integration tests demonstrate:

- data continuity,
- area_id preservation,
- cross-ward isolation,
- partial-failure isolation,
- Ward Context Store persistence,
- Wire 2 retrieval,

The remaining work is now clearly bounded.

The next major architectural task is the Main Gate, followed by final black-box validation and eventual replacement of the intentionally temporary data/model components.
