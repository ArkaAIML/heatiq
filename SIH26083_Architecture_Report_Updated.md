# SIH26083 HeatIQ: Comprehensive System Architecture Report

## 1. Purpose of this document

This document describes the **current implementation-aligned architecture**
of the SIH26083 project, **Localized Human Thermal Stress & Health Risk Early
Warning Platform (HeatIQ)**.

The original architecture report was based primarily on the architecture
diagram and project summary. This revision keeps that conceptual architecture
but reconciles it with the implementation that has since been built and
audited.

The central architectural idea remains:

> **Weather → Human Thermal Stress → Health Risk → Ward-Level Intelligence →
> Decision Support → Targeted Action**

The important implementation distinction is that HeatIQ now has explicit
**Wire 1** and **Wire 2** runtime boundaries, a **Main Gate** inside the
backend, persistent/runtime context stores, a deterministic Ward Filter,
and a Gemini-backed Recommendation Engine.

---

# 2. Current High-Level Architecture

The current backend should be understood as two related flows.

## 2.1 Wire 1: Location → Ward Intelligence

A place name starts the complete ward-processing pipeline.

```text
CLI / API Client
      │
      ▼
   Main Gate
      │
      │ place name
      ▼
    Wire 1
      │
      ├──────────────► Weather / historical data acquisition
      │
      ├──────────────► Thermal Engine
      │
      ├──────────────► Prediction Engine / ML
      │
      ├──────────────► Mortality / Health Risk
      │
      ├──────────────► Info Pool
      │

                           ▼

                           │
                           ▼
                     Main Gate
                           │
                           ▼
                         CLI /
                       Dashboard
```

Wire 1 is responsible for producing the localized intelligence for the
wards belonging to the requested location.

# 3. Main Architectural Principle

HeatIQ follows an **impact-based early-warning architecture**.

A conventional warning system may stop at:

```text
Temperature → Heatwave Warning
```

HeatIQ extends this into:

```text
Weather / Forecast
        ↓
Thermal Stress
        ↓
HTSI
        ↓
Population-Level Health Risk
        ↓
Ward-Level Risk
        ↓
Population + Resource Context
        ↓
Deterministic Ward Classification
        ↓
Forward-Looking Prediction
        ↓
Operational Recommendation
        ↓
Government Action / Alert
```

The system is therefore designed to answer:

> **Where is heat dangerous, how severe is the human impact, when is the
> critical window, which populations are vulnerable, what resources exist,
> and what should authorities do?**

# 5. Main Gate

## Role

The Main Gate is the backend entry boundary.

It lives inside:

```text
backend/
└── maingate/
```

It is responsible for exposing the backend's externally consumable API
surface and coordinating requests into the appropriate wire.

## Responsibilities

The current Main Gate design includes:

- issuing unique API keys
- storing issued API keys
- revoking/deleting API keys
- authenticating API-key-based requests
- routing incoming information
- distinguishing a place name from an area ID
- sending place names into Wire 1
- sending area IDs into Wire 2
- returning the appropriate output to the caller
- starting the backend server through the backend runtime entry point
- handling multiple incoming requests through the server/runtime

The conceptual routing is:

```text
Input
  │
  ├── place name ──► Wire 1
  │
  └── area_id ─────► Wire 2
```

The Main Gate is therefore a **traffic and interface boundary**, not a
replacement for either wire.

# 6. Wire 1

Wire 1 is the main ward-intelligence pipeline.

Its job is to take a location such as:

```text
Bhubaneswar
```

and produce the calculated ward-level state.

The current implementation performs the following broad operations:

```text
Location
   ↓
Data acquisition
   ↓
Thermal / prediction / mortality / population /
resource inputs
   ↓
Ward-level assembly
   ↓
Deterministic Ward Filter
   ↓
WardFilterResult
   ↓
WardContext storage
```

Wire 1 is executed once for a requested location.

Once it has generated the ward contexts, those contexts are available to
Wire 2 for subsequent ward-specific recommendation requests.

# 7. Data Foundation and Weather Data

The Data Foundation provides the environmental inputs required by the
analytical engines.

The prototype includes weather/history data suitable for the prediction
workflow, including the project's current multi-day hourly data foundation.

The important architectural rule is:

> **Data acquisition is upstream of the analytical engines.**

The analytical modules should consume structured data rather than each
module independently inventing its own weather acquisition path.

The current prototype also distinguishes source data from generated/cache
representations.

---

# 8. Weather History and Prediction Data

The prediction workflow requires historical and current weather information.

The prototype uses a multi-day hourly history window as part of the ML
feature construction.

The Prediction Gate / prediction integration extracts the required history
window and current observation, constructs the model feature set, and sends
it to the configured prediction artifact.

The resulting prediction is then made available to the ward-processing
pipeline.

This is an implementation refinement over the older architecture report,
which described prediction more generically but did not specify the current
history-window integration.

# 9. Thermal Engine

## Role

The Thermal Engine converts environmental conditions into human thermal-stress
information.

Its conceptual inputs include:

- temperature
- humidity
- wind speed
- solar/radiation information where available
- exposure-related information where supported

The engine produces thermal metrics such as:

- WBGT
- UTCI
- Heat Index

and the project's consolidated:

- **HTSI**

Conceptually:

```text
Temperature
Humidity
Wind
Radiation
Exposure-related inputs
        │
        ▼
   Thermal Engine
        │
        ├──► WBGT
        ├──► UTCI
        └──► Heat Index
                 │
                 ▼
                HTSI
```

The Thermal Engine owns the thermal calculation responsibility.

---

# 10. HTSI

HTSI is the project's Human Thermal Stress Index.

It is the bridge between environmental measurements and downstream
health-risk analysis.

The current Ward Filter uses HTSI as one of its primary deterministic
signals.

Conceptually:

```text
Environmental conditions
        ↓
WBGT / UTCI / Heat Index
        ↓
       HTSI
        ↓
Ward-level thermal condition
```

HTSI should not be confused with the mortality-risk score or the future
prediction score.

---

# 11. Mortality / Health Risk Layer

The Mortality component represents area/population-level health risk.

It is not an individual probability such as:

> "Person X has a 17% chance of dying."

Instead, it supplies a structured ward-level health/mortality risk signal.

The current Ward Filter can use this signal alongside HTSI and other ward
context.

Conceptually:

```text
Historical / population / thermal-health information
                     ↓
              Mortality layer
                     ↓
             mortality risk level
                     ↓
                 Ward Filter
```

The exact statistical model is an implementation detail and should not be
confused with the deterministic Ward Filter rules.

---

# 12. Info Pool

The Info Pool supplies ward-level population and vulnerability information.

Conceptually this can include:

- age-related population information
- sex/gender information where available
- occupation information
- population characteristics
- exposure-related information
- vulnerability-related aggregates

The current implementation represents this information through structured
ward records.

A critical architectural principle is:

> **The MVP performs population/ward-level targeting and does not pretend to
> know every individual's live location or exposure state.**

For example, the platform may know that a ward contains a high concentration
of an exposed population group without knowing where each individual is
standing at this moment.

---

# 13. Resource Pool

The Resource Pool supplies the response-capacity context for each ward.

The current prototype Resource Pool uses the following canonical fields:

```text
area_id
hospital_count
hospital_capacity
cooling_centre_count
distance_to_healthcare_km
resource_capacity_score
```

The prototype currently provides Resource Pool records for:

```text
WARD_001 → WARD_060
```

These values are explicitly **mock/prototype data**, not authoritative
government resource statistics.

The Resource Pool is especially important to the Recommendation Engine
because recommendations should consider both:

```text
severity
+
available response capacity
```

The Resource Pool is therefore contextual decision information, not another
thermal metric.

---

# 14. Prediction Engine / ML

The Prediction Engine is the forward-looking component.

Its purpose is to provide:

1. heat-risk prediction
2. heat-risk window / duration

The current ML integration uses the prototype data foundation to construct
the model feature set from the configured history/current-observation
inputs and runs inference against the configured prediction artifact.

The resulting PredictionOutput is made available to the Ward Filter and
downstream decision-support pipeline.

Conceptually:

```text
Hourly historical window
        +
Current observation
        +
Required contextual features
        │
        ▼
Prediction Gate
        │
        ▼
ML Prediction Artifact
        │
        ├──► probable future heat risk
        └──► heat-risk window
```

The Prediction Engine is distinct from the Thermal Engine.

It does not replace current-condition thermal calculations.

---

# 15. Ward Filter

The Ward Filter is the **deterministic ward-intelligence and classification
boundary**.

This is an important update from the original report.

The current Ward Filter is not merely a generic pass-through or geographic
selector. It:

1. receives structured inputs for a ward
2. combines them into a `WardContext`
3. evaluates deterministic policy rules
4. selects the applicable severity
5. produces a human-readable condition message
6. records triggered conditions and recommended actions
7. returns a structured `WardFilterResult`

The relevant inputs include:

```text
ThermalOutput
PredictionOutput
MortalityOutput
InfoPoolRecord
ResourcePoolRecord
```

The output is therefore much richer than a simple ward number or color.

---

# 16. InfoSmasher

`InfoSmasher` is the assembly component inside the Ward Filter.

Its job is to assemble the already-structured information belonging to
**one ward** into one validated `WardContext`.

Conceptually:

```text
ThermalOutput
PredictionOutput
MortalityOutput
InfoPoolRecord
ResourcePoolRecord
        │
        ▼
    InfoSmasher
        │
        ▼
    WardContext
```

It performs:

- type validation
- area-ID matching
- timestamp preservation
- context validation

It does **not** itself calculate severity.

That responsibility belongs to the deterministic rules/engine layer.

This distinction is important:

```text
InfoSmasher
    = assemble + validate

Ward Filter Rules
    = evaluate + classify
```

---

# 17. Deterministic Ward Rules

The Ward Filter contains deterministic rules that classify the situation.

The rules combine signals such as:

- HTSI
- mortality risk
- vulnerability score where available
- resource capacity
- prediction hazard score

The rule system uses explicit priorities and reason codes.

Examples of rule families include:

```text
EXTREME
CRITICAL
HIGH
MODERATE
LOW
```

A rule can also provide:

- reason code
- recommended action
- human-readable condition message
- priority

The deterministic engine is deliberately separate from Gemini.

Gemini does not decide whether a ward is `HIGH`, `CRITICAL`, or `EXTREME`.

The Ward Filter does that.

---

# 18. Missing Data Behaviour

The current rules engine has been updated so that missing data does not
invalidate an entire ward.

A rule that requires a missing field is skipped, while unrelated rules
continue evaluating.

Conceptually:

```text
resource_score = NULL
        ↓
resource-dependent rule
        ↓
SKIP

thermal-dependent rule
        ↓
STILL EVALUATE
```

Similarly:

```text
mortality = NULL
```

should only disable mortality-dependent rules.

The engine distinguishes intentional missing-data handling from actual
programming errors.

This prevents a single unavailable field from causing many wards to fall
through to an unrelated generic rule.

---

# 19. WardFilterResult

The Ward Filter returns a structured result rather than only a severity tag.

The result can expose information including:

```text
area_id
timestamp
severity
condition_message
triggered_conditions
recommended_actions
calculation_status
method_version
WardContext
```

The current CLI is intended to expose this **raw Ward Filter output** after
Wire 1 runs.

This is important because the Ward Filter output is itself valuable system
intelligence and should not be hidden behind a decorative frontend.

---

# 20. Wire 1 Storage

Wire 1 stores the generated ward context/results in the existing runtime
context store.

The important relationship is:

```text
Wire 1
  ↓
WardContext / WardFilterResult
  ↓
Wire 1 storage
```

This stored context becomes the source of truth for Wire 2.

The architecture does not require Wire 2 to recalculate any of the
upstream analytics.

---

# 21. Wire 2

Wire 2 is the ward-specific recommendation loop.

It begins only after Wire 1 has produced the required ward context.

For example:

```text
input Bhubaneswar
        ↓
Wire 1
        ↓
WARD_059 context exists
        ↓
WARD_059
        ↓
Wire 2
```

If the user requests:

```text
WARD_059
```

before Wire 1 has generated that ward's context, Wire 2 must reject the
request.

This creates an explicit dependency:

> **Wire 2 depends on Wire 1's generated ward context.**

Wire 2 must not silently rerun Wire 1.

---

# 22. Recommendation Engine

The Recommendation Engine is the **operational decision-support layer**.

This is another important update from the original report.

The current intended flow is:

```text
WardContext
    ↓
Recommendation Engine
    ↓
Gemini
    ↓
RecommendationOutput
```

The Recommendation Engine does not recalculate HTSI, mortality risk,
vulnerability, resource scores, or ML predictions.

Those are already calculated upstream.

Instead, it asks:

> **Given this exact ward's calculated state, population context, prediction,
> and available resources, what should authorities do?**

---

# 23. Gemini Integration

Gemini receives the selected ward's structured information.

For example:

```text
WARD_059
```

causes Wire 2 to retrieve **WARD_059's** context and send that context to
the Gemini provider.

Gemini must not receive all wards when only one ward was requested.

The structured context can include:

```text
area_id
timestamp

thermal
prediction
mortality
info_pool
resource_pool

severity
condition_message
triggered_conditions
recommended_actions
calculation_status
method_version
```

The exact serialized payload should follow the project's existing schemas
rather than creating a competing ward-data model.

---

# 24. Gemini's Responsibility

Gemini is an operational recommendation generator, not the deterministic
risk calculator.

Its response should turn ward intelligence into an actionable procedure.

A recommendation may address:

- immediate actions
- population priorities
- cooling-centre use
- healthcare preparation
- water/hydration support
- outdoor-worker protection
- emergency-resource positioning
- outreach
- monitoring
- escalation conditions

The response should explain:

```text
WHAT to do
WHY to do it
HOW to do it
WHAT to prioritize
WHAT resources to allocate
WHERE to allocate them
WHAT to monitor
WHEN to escalate
```

Gemini must use the supplied ward data and must not invent facilities,
capacities, population numbers, or resources that are not present in the
input.

---

# 25. Recommendation Output

Gemini's response is converted into the existing `RecommendationOutput`
structure.

The recommendation belongs to the selected area ID.

Conceptually:

```text
WARD_059
   ↓
RecommendationOutput(
    area_id = WARD_059,
    recommendation = Gemini response
)
```

The recommendation should not modify the original WardContext.

The deterministic Ward Filter result also remains unchanged.

---

# 26. Wire 2 Runtime Storage

Wire 2 holds recommendation state as runtime/temporary state.

This is intentionally different from treating recommendations as a
permanent historical database.

The essential property is ward isolation:

```text
WARD_059
    ↓
recommendation_059

WARD_060
    ↓
recommendation_060
```

A recommendation generated for one ward must never be returned for another
ward.

The runtime loop can therefore continue:

```text
WARD_059
   ↓
Gemini recommendation

WARD_060
   ↓
Gemini recommendation

WARD_012
   ↓
Gemini recommendation
```

without rerunning Wire 1.

# 36. Important Architectural Boundaries

The following boundaries should be preserved.

## Boundary 1: Thermal calculations

Thermal calculations belong to the Thermal Engine.

## Boundary 2: Deterministic risk classification

Ward severity belongs to the Ward Filter rules.

## Boundary 3: Prediction

Future-risk prediction belongs to the Prediction Engine.

## Boundary 4: Ward context assembly

Combining structured inputs belongs to InfoSmasher.

## Boundary 5: Wire 1 / Wire 2

Wire 1 produces ward intelligence.

Wire 2 consumes a previously generated ward context and produces an
operational recommendation.

## Boundary 6: Gemini

Gemini interprets already-calculated intelligence.

It does not replace deterministic calculations.

## Boundary 7: Presentation

CLI/dashboard components render outputs.

They do not recalculate backend state.

# 37. What Changed From the Earlier Architecture Description

The original report described the conceptual architecture correctly but was
too abstract in several places.

The current implementation clarifies the following.

### 37.1 Wire 1 is now an explicit runtime pipeline

Instead of describing the modules as a mostly linear conceptual chain,
Wire 1 explicitly orchestrates the structured inputs and produces
`WardContext` / `WardFilterResult`.

### 37.2 InfoSmasher is an explicit assembly boundary

The inputs are assembled and validated before deterministic Ward rules are
evaluated.

### 37.3 Ward Filter is deterministic

The Ward Filter does not merely target wards. It also evaluates explicit
rules and emits severity, reason/message, triggered conditions, and
recommended actions.

### 37.4 Resource Pool is a concrete ward-level dependency

The prototype Resource Pool currently covers all 60 Bhubaneswar wards.

### 37.5 Prediction is integrated through a real feature pipeline

The current implementation uses a multi-day hourly history window and current
observation to construct ML features before inference.

### 37.6 Wire 2 is a separate recommendation loop

Selecting a ward after Wire 1 does not rerun the entire location pipeline.

### 37.7 Gemini is downstream of deterministic intelligence

Gemini receives the selected ward's structured context and produces an
operational recommendation.

### 37.8 Wire 2 recommendations are runtime state

The recommendation does not become a new permanent source of truth for
Ward 1.

### 37.9 Main Gate is an actual backend access boundary

It handles API keys, routing, and server access rather than being only a
conceptual gateway.

```text
        vs.
```

# 39. Privacy and Individual-Level Targeting

The current MVP should not claim to know the exact real-time state of every
person.

The system primarily operates at:

```text
ward / grid
+
population group
+
available resource
```

level.

Future personalized targeting could require authorized integration with
government, telecom, operating-system, or third-party systems.

A future privacy-preserving architecture should avoid unnecessarily
centralizing:

```text
identity
+
exact location
+
vulnerability
+
historical exposure
```

The current prototype does not require this personalized infrastructure.

```text
        ↓
Alert infrastructure
        ↓
Targeted public message
```

A representative alert may be:

```text
CRITICAL HEAT RISK

Extreme heat risk from 11 AM to 3 PM today.

Please avoid unnecessary outdoor exposure
and move to a cool environment.
```

The actual message should be generated from the relevant localized risk
state and not from an arbitrary global temperature threshold.

# 44. Architecture Rules to Preserve

### Rule 1: Thermal Engine owns thermal calculations

### Rule 2: Mortality represents population-level health risk

### Rule 3: Prediction is a separate future-risk path

### Rule 4: InfoSmasher assembles one ward's structured inputs

### Rule 5: Ward Filter owns deterministic severity classification

### Rule 6: Missing data must only disable rules that actually require it

### Rule 7: Resource Pool provides response-capacity context

### Rule 8: Wire 1 produces the canonical ward context

### Rule 9: Wire 2 consumes an existing ward context

### Rule 10: Gemini interprets ward intelligence rather than recalculating it

### Rule 11: Gemini output must not modify Wire 1's canonical context

### Rule 12: Main Gate owns external request/API-key routing

### Rule 13: CLI/dashboard are presentation clients

### Rule 14: Prototype/mock data must not be presented as authoritative data

## 47. One-Line Mental Model

> **HeatIQ takes environmental and forecast information, turns it into
> human thermal and population-level health intelligence, localizes that

> resource-aware operational recommendation through Gemini.**
