# HeatIQ Data Contract

**Version:** 0.1  
**Status:** Development Baseline  
**Project:** HeatIQ — Extreme Heatwave Early Warning & Human Thermal Stress System

---

## 1. Purpose

This document defines the shared data interface between the major HeatIQ components:

1. Data Ingestion & Thermal Calculation Engine
2. ML Prediction Engine
3. Heat-Health Risk Engine
4. Recommendation Engine
5. Backend API

The objective is to allow different components to be developed independently while maintaining a consistent schema.

The contract may evolve as real datasets are evaluated. Breaking changes must update the contract version.

# 3. Core Risk Model

HeatIQ distinguishes between four concepts:

```text
HAZARD
    +
EXPOSURE
    +
VULNERABILITY
    +
ADAPTIVE CAPACITY
    ↓
HEAT-HEALTH RISK
```

Conceptually:

```text
Risk = f(Hazard, Exposure, Vulnerability, Adaptive Capacity)
```

Where:

- **Hazard** represents environmental heat and thermal stress.
- **Exposure** represents how many people/assets are exposed.
- **Vulnerability** represents population susceptibility.
- **Adaptive Capacity** represents the area's ability to respond.

The ML model primarily predicts future **thermal hazard**.

The Risk Engine combines this prediction with contextual information to determine operational heat-health risk.

# 5. Fundamental Observation Unit

The preferred canonical observation is:

> One record = one geographic area at one timestamp.

Example:

```text
area_id   = WARD_017
timestamp = 2026-05-20T14:00:00+05:30
```

### Geographic Resolution

Preferred:

```text
Ward
```

Fallback:

```text
Grid Cell
District
```

The final resolution depends on dataset availability.

### Temporal Resolution

Preferred environmental resolution:

```text
Hourly
```

Daily aggregates may additionally be produced for multi-day forecasting.

# 6. Field Status Definitions

Every field is assigned one of the following statuses.

| Status | Meaning |
|---|---|
| `REQUIRED` | Core field expected by the pipeline |
| `PROVISIONAL` | Intended field, dependent on data availability |
| `EXPERIMENTAL` | Candidate feature requiring validation |
| `DERIVED` | Generated from other fields |

| `latitude` | float | degrees | PROVISIONAL | Area centroid latitude |

# 9. Thermal Index Schema

These values are produced by the Thermal Calculation Engine.

| Field | Type | Unit | Status | Description |
|---|---|---|---|---|
| `heat_index_c` | float | °C | DERIVED | Heat Index |
| `utci_c` | float | °C | DERIVED | Universal Thermal Climate Index |
| `wbgt_c` | float | °C | DERIVED | Wet Bulb Globe Temperature |

Thermal indices must only be calculated when their required inputs and applicability conditions are satisfied.

Missing inputs must not be silently fabricated.

The implementation must document:

```text
Formula / library
Required inputs
Units
Assumptions
Applicability range
Fallback behaviour
```

# 14. Primary ML Prediction Target

## 14.1 Prototype Target

The primary ML task is:

> Predict future thermal-health hazard severity for each geographic area over a 1–5 day forecast horizon.

Two formulations will be evaluated.

### Regression

Predict a future thermal-stress quantity such as:

```text
future_max_utci_c
```

Conceptually:

```text
X(t) → maximum UTCI at t + horizon
```

### Classification

Predict whether future conditions cross a scientifically defined severe thermal-stress threshold.

Example target:

```text
severe_thermal_stress = 0 or 1
```

The exact threshold will follow the selected thermal-index methodology.

# 16. Health Outcome Prediction

Direct mortality prediction is NOT part of the initial validated prototype.

HeatIQ will not claim that a model predicts heat-induced deaths unless appropriate historical health-outcome labels are obtained.

Potential future targets include:

```text
excess hospital admissions
hospitalization surge probability
heat-related illness counts
excess all-cause mortality
```

Such models require genuine historical health labels.

Synthetic risk scores must never be presented as observed mortality.

# 17. ML Model Strategy

The model development sequence is:

## Baseline A — Rule-Based

Establish a non-ML thermal-stress baseline.

## Baseline B — Classical ML

Evaluate:

```text
Logistic Regression
Random Forest
```

where appropriate.

## Primary ML Model — XGBoost

XGBoost will be evaluated as the primary tabular prediction model.

Reasons include:

- Strong performance on tabular data
- Handles nonlinear interactions
- Relatively low compute requirements
- Suitable for free Google Colab
- Supports feature importance / SHAP analysis

## Deep Learning Experiment — GRU

A lightweight GRU may be evaluated for temporal sequence modelling.

Example input:

```text
[T(t-48), ..., T(t)]
[RH(t-48), ..., RH(t)]
[UTCI(t-48), ..., UTCI(t)]
...
```

Output:

```text
future thermal hazard
```

The GRU will only be retained if it meaningfully improves validation performance.

# 18. Train / Validation / Test Strategy

Time-dependent observations must preserve chronology.

Preferred split:

```text
Past
│
├──────────────┬───────────┬──────────────► Future
Training       Validation   Test
```

Random shuffling of time-series observations should not be used when it would allow future information to influence past predictions.

Exact date boundaries will depend on dataset coverage.

---

# 19. Data Leakage Policy

A feature may only be used if it would realistically be available when the prediction is generated.

| Feature | Allowed |
|---|---|
| Historical temperature | YES |
| Current observed temperature | YES |
| Historical UTCI | YES |
| Population statistics known beforehand | YES |
| Weather forecast available at prediction time | YES |
| Tomorrow's observed temperature | NO |
| Future hospital admissions | NO |
| Future mortality observations | NO |

ML preprocessing must also avoid leakage.

For example:

- Scalers must be fitted on training data.
- Imputation statistics must be learned from training data.
- Future observations cannot be used in rolling/lag calculations.

```text

        +

        +

        ↓
```

Output:


Risk-category thresholds and weights must be documented and justified.

They must not be presented as clinically validated unless such validation has actually been performed.

# 23. Recommendation Engine

The Recommendation Engine consumes:

```text
Heat-health risk
+
Hazard characteristics
+
Vulnerability
+
Available resources
+
Geographic context
```

and produces actionable recommendations.

Initial recommendations will use deterministic rules.

Example:

```text
IF
    risk_level == EXTREME
AND
    elderly_fraction is high
AND
    cooling_capacity is low

THEN
    priority = CRITICAL
```

Possible actions:

```text
Issue targeted heat warning
Activate/open cooling facilities
Prioritize elderly outreach
Prepare medical resources
Increase drinking-water availability
Advise reduction of strenuous outdoor activity
```

Final public-health recommendations must be aligned with authoritative guidance before deployment.

# 25. Missing Data Policy

Missing values must not be silently fabricated.

Rules:

1. Preserve missing values as `null` / `NaN` during ingestion.
2. Record missingness before imputation.
3. Validate required variables before thermal calculations.
4. ML imputation must be fitted using training data only.
5. Future observations must never be used for imputation.
6. Critical missing inputs should produce an insufficient-data state when reliable inference is impossible.

Example:

```json
{
  "status": "INSUFFICIENT_DATA",
  "area_id": "WARD_017",
  "missing_fields": [
    "temperature_c",
    "relative_humidity_pct"
  ]
}
```

# 33. Development Principle

The architecture must maintain the following separation:

```text
THERMAL ENGINE
"What are the physical thermal conditions?"
        │
        ▼
ML PREDICTION ENGINE
"What thermal hazard is likely in the next 1–5 days?"
        │
        ▼
RISK ENGINE
"How serious is that hazard for this area and population?"
        │
        ▼
RECOMMENDATION ENGINE
"What should be done about it?"
```

This separation allows HeatIQ to remain modular, explainable, testable and scientifically defensible.

---

# 34. Primary Product Objective

HeatIQ should not merely answer:

> "Where will it be hottest?"

The system should ultimately answer:

> **"Where is dangerous human thermal stress likely to occur in the next 1–5 days, how serious is the resulting heat-health risk for the exposed population, and what interventions should be prioritized?"**
